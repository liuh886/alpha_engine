# Model Run Bundle v2

Status: additive compatibility contract  
Boundary: `research_only=true`, `trade_ready=false`

## Purpose

Model Run Bundle v2 is the durable interface between governed Python research workflows and the static frontend. It separates immutable run identity, lightweight summary evidence, heavy ledgers and research decisions so local, preview and formal channels can use one package contract without weakening the formal allow-list.

## Immutable identities

- `model_family_id`: stable research family.
- `model_version_id`: frozen model, universe and portfolio contract.
- `run_id`: one governed execution of that version.
- `bundle_id`: SHA-256 of the canonical manifest payload with `bundle_id` omitted.

All identity values are lowercase slug identifiers. A bundle must bind every section by SHA-256 and byte size.

## Channels and statuses

| Channel | Permitted statuses | Meaning |
| --- | --- | --- |
| `local` | `local_only`, `blocked`, `rejected` | workstation review only |
| `preview` | `ci_validated_preview`, `blocked`, `rejected` | branch-scoped governed evidence |
| `formal` | `accepted_formal_baseline` | accepted named baseline only |

A preview or local record cannot enter the formal catalog. No channel may set `trade_ready=true`.

## Bundle layout

```text
manifest.json
summary.json
performance.json
risk.json
robustness.json
portfolio.json
trades.json
attribution.json
diagnostics.json
lineage.json
decision.json
```

`manifest.json` and `summary.json` are required. Other sections declare one of:

- `available`;
- `not_applicable`;
- `not_computed`;
- `not_retained`;
- `blocked_by_source`.

Unavailable sections require a reason and must not have a path, hash or byte size. Available sections require all three.

## Model kinds

- `rules_based_allocation`;
- `cross_sectional_ranker`;
- `forecast_model`.

Required evidence and frontend language are selected by `model_kind`. Allocation models must not receive stock-picking interpretation. Rankers must not receive state-machine interpretation unless exported explicitly.

## Canonical metrics

Metrics use stable IDs rather than display labels. Each record includes:

```text
metric_id
value
unit
direction
estimator
annualization
sample_count
scope
availability_status
unavailable_reason
```

The initial registry includes total and annualized return, benchmark and excess return, volatility, Sharpe, information ratio, max drawdown, turnover, transaction cost, IC, rank IC and ICIR. Missing and unavailable states are first-class and never represented by stringified null values.

## Comparability

`comparability_key` contains market, universe, benchmark, start/end dates, trace frequency, horizon, rebalance contract and cost contract. Exact equality is required for like-for-like ranking. Incompatible records may be displayed descriptively but cannot receive winner highlighting.

## Decision receipt

`decision.json` is generated by a governed evidence process and supports:

- `supported`;
- `not_supported`;
- `blocked`.

Every gate and claim binds source section paths and SHA-256 values. The browser may display or invalidate a receipt but cannot strengthen, synthesize or reinterpret its verdict.

## v1 compatibility

The current three formal v1 packages remain the production source during one additive compatibility period. A temporary adapter may map them into the v2 domain model. Removal of the v1 reader is permitted only after all three accepted baselines have v2 parity, rollback fixtures and production verification.
