## 3. 第一批：删除确定残留

### A. 删除旧前端解析、类型和孤立夹具

- **改动：** 把归因视图实际需要的类型迁到已有 Bundle v2 / FormalRunEvidence 类型，
  随后删除上述六个旧文件及无调用类型、只服务旧链的测试。
  删除没有源码或构建配置引用的 `@radix-ui/react-label`、`@radix-ui/react-select` 声明并更新 lockfile。
- **保留：** 正式归因视图、现行 Bundle v2 解析器、哈希/大小校验、availability、报告和持仓类型。
- **收益：** 少一套旧模型和旧 formal 的 Interface；类型与实现集中在现有 EvidenceBundle Module。
  闲置依赖的收益先按维护面计，不预先承诺 JS 体积下降。
- **风险：低。** 类型引用必须先迁移；共享解析器仍支持封存格式，不按 local/preview 枚举名称误删。
- **验收：** AST/全仓调用复查、类型、lint、受影响测试、构建；五策略归因及缺失证据呈现一致。

### B. 删除休眠外部市场比较路径

- **改动：** 收窄 PerformanceCharts 的现有调用，删除未被当前页面启用的 `market` 加载分支、
  `useMarketComparisons.ts`、`market-evidence.ts` 和仅服务这条路径的测试/类型。
- **保留：** 正式报告内提供的基准选择、期间收益、回撤、多序列比较及图表。
  后端市场证据和研究用数据不属于此项删除范围。
- **收益：** 减少 534 行旧模块及图表周围的休眠状态；比较逻辑只需理解正式报告的实际输入。
- **风险：低至中。** 不能连同正在使用的 benchmark control、归因或持仓虚拟滚动一起删除。
- **验收：** 五策略期间/基准切换结果一致；比较控件不请求退役 `/data/market-evidence/`；
  桌面、平板、手机交互与布局通过。

### C. 统一默认操作入口

- **改动：** 清理 Makefile 默认帮助和已退役产品入口，README 命令补齐必需参数。
  日常操作只指向现有 `alpha data`、`alpha ops`、现有控制台和维护工作流；
  重研究使用现有受治理 `alpha research` 路径。
  退役无当前消费、固定生成空多市场结果的 `model-ops` CLI/投影模块，先检查手工调用和测试依赖。
- **保留：** 有真实调用的研究计算模块、训练合同、PaperTradingLedger 等共享能力及封存研究证据。
  退役源文件按既有 archive manifest 留下 Git revision/hash，不新建归档制度。
- **收益：** 操作者不会被默认帮助引导到已退出产品的界面或没有真实数据的状态入口。
- **风险：低至中。** 不把手动研究库的存在视为应整包删除的依据。
- **验收：** 当前帮助和 README 中每条维护命令可运行；退役命令不再触发旧路径；
  现有三组 CLI 能力、MCP 实际调用者及五策略运行不受误删影响。

## 4. 第二批：收敛运行与验证职责

### D. 让环境医生使用现有健康事实

- **改动：** `doctor.py` 的当前运行判据复用现有 SystemHealth / 正式证据校验 Module。
  SQLite、MLflow、旧导出只在相关研究合同需要它们时参与该合同的诊断。
  展示依赖环境、数据时效、策略阻塞和研究权限各自影响的范围。
- **收益：** 运行状态与本地诊断使用同一事实来源，减少无关失败告警和人工排查。
- **风险：中。** 必须继续揭示真实数据缺口、损坏证据和权限限制；不能把原失败简单改为成功。
- **验收：** 删除可重建索引不会把有效核心运行判为坏；损坏正式分节仍失败；
  过时、缺失和训练受阻保持原合同含义；诊断不联网、不训练、不改 canonical evidence。

### E. 本地完整校验只执行一份检查清单

- **改动：** 复用现有 `src/release/quality.py` 执行器，收敛 Makefile `ci` 与 release quality 的重复清单；
  归并 `npm test` 与已经含测试的 build。两条旧清单的检查要求取并集，保留 Web 退役检查、
  CI 治理、类型、lint、Python 测试、skip accounting、浏览器和打包。
- **收益：** 成功的完整本地验证从四轮 Vitest 收敛为一轮；同一执行范围内安装、Python 全量测试等各做一次。
  不同输入的候选验证、PR 验证和部署后验证仍各有职责。
- **风险：中。** 现有质量回执中的检查覆盖需要明确迁移；不能把没有单独执行的命令伪造为 passed。
- **验收：** 用执行记录核对每项门禁实际运行且无重复；注入单测、构建、浏览器和未批准 skip 失败均阻断；
  质量回执仍绑定当前 revision，旧封存回执保留原义；记录前后耗时和人工步骤。

### F. 同一自动刷新候选只进行一次完整 CI

- **改动：** 自动候选以现有 exact-SHA dispatch 为验证权威，普通工程 PR 保留正常 PR 检查。
  收掉可信自动候选的重复 PR 重型执行；完整保留派发、等待成功及 merge head 匹配。
- **收益：** 六个已观察候选的双重完整校验模式收敛为每候选一次，减少等待和失败排查噪声。
- **风险：中至高。** 实施前核对分支保护与 check 身份；可信候选不能只按 actor 或可伪造的分支名判断。
  PR 事件与 dispatch 的先后变化不能造成误取消、required check 永久等待或“跳过即成功”。
  若无法保持这些条件，该项保留现状。
- **验收：** 自动候选、普通 PR、候选 SHA 更新、失败候选、重新执行均覆盖；
  每次合并都有该精确候选的成功证明，失败不能变为可合并；真实受审刷新完成一次端到端验收。

**2026-10-22 审计结论：保留现状。** 同一候选 head 的两次运行并非相同验证输入：
PR 事件检出 GitHub test-merge commit，dispatch 检出并核对精确 candidate commit。
生产者显式派发、等待成功、匹配候选 head 合并，再验证实际 merge SHA 的 Pages 发布；这些职责继续保留。

本次直接查询仓库 API：`main` 的 `protected=false`，适用分支规则和 rulesets 均为空。
没有可复用的受治理合并队列或强制最新基线机制。`--match-head-commit` 只约束候选 head，
不绑定合并时的 base；因此不能用它代替 test-merge 输入的验证，也不声称当前双重 CI 消除了全部基线竞态。
仅统一并发键会误取消不同输入的证明，仅跳过 PR 重型步骤会失去该输入的覆盖。

将 PR 检查改为等待 dispatch 还需新增可信来源识别、完整差异分类、head/base 绑定、
有界等待和失败传播；这会增加永久协调逻辑，仍需解决合并输入覆盖。
本轮不以削弱检查或引入另一套协调机制换取去重，不修改仓库保护设置或工作流。
只有已有受治理机制能够证明候选验证覆盖实际合并输入，并取得明确运行收益后，才重新评估此项。
